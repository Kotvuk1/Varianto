# PRD — Trading Lab

Версия: 0.1 (черновик). Дата: 2026-11-03.
Источник требований: `docs/INTERVIEW_SUMMARY.md` (подтверждено пользователем), ограничения доступа к Binance: `docs/PROJECT_STATUS.md`.

Соглашения документа:
- Термины SMC и технические термины даны на английском.
- Метка **(предложение)** означает, что пункт не зафиксирован в резюме интервью и предложен документом; его нужно подтвердить.
- Метка **(открытый вопрос)** означает, что решение не принято; ссылка вида OQ-xx ведёт в раздел 12.
- Архитектурные решения в этот документ не входят; они фиксируются в следующем этапе (архитектура, ADR в `docs/DECISIONS/`).

## 1. Обзор и цель продукта

### 1.1 Что это
Trading Lab — образовательная платформа по техническому анализу криптовалют. Пользователь тренируется на реальных исторических и живых графиках Binance USDⓈ-M Futures, размечает структуру рынка, принимает торговые решения в симуляции и получает подробный разбор ошибок.

### 1.2 Цель
Дать пользователю среднего уровня практику анализа SMC на реальных графиках с объективной проверкой и разбором ошибок, чтобы он системно закрывал слабые места, а не просто читал теорию.

### 1.3 Целевой пользователь
| Параметр | Значение |
|---|---|
| Кто | Один пользователь — владелец проекта. Модель данных сразу многопользовательская; несколько пользователей возможны в будущем |
| Уровень | Средний: знает базу, нужна практика на реальных графиках и подробный разбор ошибок; теория подаётся короткими справками внутри заданий |
| Школа анализа | SMC |
| Устройства | Телефон и ноутбук на равных; mobile-first, управление касаниями |
| Язык | Русский интерфейс, термины SMC на английском с расшифровкой |

### 1.4 Модули
| Модуль | Статус |
|---|---|
| Market Structure Analyzer (SMC) | MVP |
| Trading Challenge | MVP |

## 2. Принципы продукта

1. **Правильность определяет детерминированный алгоритм.** Оценку «верно/неверно» всегда выдаёт чистая TS-библиотека SMC/Price Action. Текст разбора и (позже) ИИ могут только объяснять уже проверенные факты.
2. **Только реальные данные.** Источник: Binance USDⓈ-M Futures (для разработки и тестов — архив data.binance.vision). Синтетические данные в MVP не используются. Если они появятся позже, они должны быть явно помечены в интерфейсе.
3. **Нейтральные цвета, без «победа/поражение».** Свечи синие/оранжевые (монохром как настройка). Красный и зелёный не используются для обозначения победы или поражения; результат в R показывается нейтральным цветом; разбор подаётся иконками и формой меток, а не «светофором».
4. **Mobile-first.** График на весь экран, инструменты в нижней панели, разбор в нижней шторке; всё управляется касаниями. Ноутбук поддерживается наравне.
5. **Практика важнее теории.** Теория — короткие справки внутри заданий, не отдельные курсы.
6. **Рабочий терминал.** Максимум места графику, минимум декора. Без XP, ачивок и рейтингов.

## 3. Область продукта

### 3.1 В MVP
- Загрузка рыночных данных браузером напрямую с Binance (REST + WebSocket), таймфреймы 15m/1H/4H/1D, только объём как индикатор.
- График на Lightweight Charts со слоем разметки (объекты с привязкой к времени и цене), управление касаниями.
- Библиотека SMC/Price Action (swing, HH/HL/LH/LL, BOS, CHoCH, internal/external structure, Liquidity sweep, Order Block, FVG, шесть свечных моделей).
- Market Structure Analyzer: режимы «Разметка» и «Вопрос».
- Price Action Trainer: «Найди модель», «Проведи уровень», «Контекст».
- Trading Challenge: LONG/SHORT/WAIT, SL/TP, обоснование, проигрывание, результат в R, оценка качества решения, три уровня сложности.
- Свободный терминал: любая пара USDⓈ-M, сохранение разметки, «Проверить мою разметку».
- Разбор из шести частей на шаблонах по распознанным ошибкам.
- Прогресс: точность по навыкам, журнал ошибок, адаптивная подборка, статистика Challenge, повышение сложности, дневная цель, мягкая серия, экран «Слабые места».
- Вход через Google и magic link; синхронизация между устройствами.
- Тёмная и светлая темы; русский интерфейс с вынесенными текстами.

### 3.4 Технические риски
| ID | Риск | Последствие | Смягчение (в рамках требований) |
|---|---|---|---|
| R-01 | Binance возвращает 451 из облака разработки и, вероятно, с серверов Vercel в США | Сервер не может загружать данные | Данные грузит браузер (зафиксировано); тесты на архиве data.binance.vision |

| R-04 | Лимиты Binance (вес запросов, лимит WebSocket-подписок) | Ошибки при частой загрузке | Кэширование, понятное сообщение об ошибке (NFR-REL) |
| R-05 | SMC-понятия частично субъективны (OB, sweep, внутренняя структура) | Спорные оценки | Явные формализованные правила, тесты на реальных данных, документирование допущений |
| R-06 | Supabase Free приостанавливает неактивный проект | Недоступность входа и прогресса | Автопинг (NFR-FREE) |
| R-07 | Ограничения бесплатных тарифов (Vercel Hobby, Supabase Free: лимиты почты magic link, размер БД) | Блокировка функций | Мониторинг лимитов; переход на платный тариф настройкой |
| R-08 | Проверка ответа выполняется на клиенте (сервер не видит Binance) | Принципиально возможна подмена результата; для одного владельца неважно, для многопользовательского режима важно | Зафиксировать в архитектуре; учесть в v2 (OQ-04) |
| R-09 | Один разработчик проверяет только с телефона | Нет автоматического визуального контроля на ноутбуке | Превью Vercel на каждом PR; Playwright-проверки (предположение, решается в архитектуре) |

## 7. User Flows

### 7.1 Первый вход
1. Пользователь открывает сайт; видит экран входа с кнопками «Войти через Google» и «Войти по ссылке на email» (если доступ без входа не разрешён; OQ-14).
2. Выбирает Google: проходит согласие Google и возвращается в приложение. Либо вводит email: получает письмо с magic link и открывает его на этом же или другом устройстве.
3. Приложение создаёт профиль пользователя и открывает главный экран.
4. Главный экран предлагает выбор модуля и показывает ежедневную цель.
5. При первом запуске задания показывается короткая подсказка по управлению касаниями (прокрутка, зум, выбор инструмента) **(предложение)**.

### 7.2 Сессия Market Structure (режим «Разметка»)
1. Пользователь выбирает Market Structure → «Разметка», пару и таймфрейм (пары BTC/ETH/SOL; 15m/1H/4H/1D) и сложность.
2. Приложение загружает историю из Binance и выбирает фрагмент реальной истории; график открывается на весь экран.
3. Над графиком показывается короткая справка по проверяемому понятию.
4. Пользователь выбирает в нижней панели инструмент (например, Swing High) и касается свечи; повторяет для остальных понятий.
5. При необходимости перемещает или удаляет метки.
6. Нажимает «Проверить».
7. Алгоритм сравнивает метки с эталоном с учётом допуска; результат: совпавшие, пропущенные, лишние.
8. Снизу открывается шторка с разбором из шести частей; эталонная разметка показывается поверх графика.
9. Ошибки записываются в журнал; точность по навыкам обновляется.
10. Пользователь переходит к следующему заданию или возвращается на главный экран.

### 7.3 Trading Challenge: от выбора до разбора
1. Пользователь выбирает «Trading Challenge» и сложность (лёгкий / средний / сложный).
2. Приложение выбирает случайный момент реальной истории BTC/ETH/SOL; дата скрыта.
3. График показывает историю до момента решения; пользователь может переключать таймфреймы 15m/1H/4H/1D без доступа к будущему.
4. Пользователь выбирает LONG, SHORT или WAIT.
5. Для LONG/SHORT пользователь ставит на графике SL и TP; без них кнопка подтверждения недоступна, сообщение объясняет причину.
6. Пользователь выбирает причины из списка и при желании добавляет текст.
7. Нажимает «Подтвердить»; запускается проигрывание свеча за свечой.
8. Проигрывание останавливается при достижении SL, TP или лимита времени.
9. Открывается разбор: результат в R (для позиции), оценка качества решения отдельно от исхода, правильная разметка ситуации, 6-частный разбор.
10. Результат и ошибки сохраняются; статистика Challenge обновляется.
11. Пользователь запускает следующий сценарий или выходит.

### 7.4 Price Action «Контекст»
1. Пользователь выбирает Price Action → «Контекст».
2. Приложение показывает график реальной истории с выделенной свечной моделью (например, пин-бар).
3. Пользователь определяет контекст: наличие Liquidity sweep, Order Block, ближайшего уровня и направление старшего тренда **(перечень вариантов ответа уточняется; OQ-16)**.
4. Подтверждает ответ.
5. Алгоритм сравнивает ответ с эталонным контекстом.
6. Открывается шторка с 6-частным разбором: значима модель в этом контексте или нет и почему.
7. Результат и тип ошибки записываются в прогресс.

### 7.5 Терминал с проверкой разметки
1. Пользователь открывает «Терминал»; приложение загружает последнюю использованную пару или BTCUSDT по умолчанию **(предложение)**.
2. Через поиск выбирает любую пару USDⓈ-M; график обновляется в реальном времени по WebSocket; незакрытая свеча помечена.
3. Размечает график инструментами из панели; метки сохраняются в аккаунт автоматически.
4. Нажимает «Проверить мою разметку».
5. Алгоритм SMC запускается на закрытых свечах текущего графика и сравнивает с разметкой пользователя.
6. Открывается шторка с разбором (совпало / пропущено / лишнее и объяснения).
7. Пользователь вносит правки и повторяет проверку.

### 7.6 Просмотр «Слабых мест»
1. Пользователь открывает «Прогресс»; первым показывается экран «Слабые места».
2. Видит навыки, отсортированные от наименьшей точности, с числом попыток.
3. Нажимает на навык: видит журнал ошибок по нему и кнопку «Тренировать».
4. Кнопка запускает серию заданий, подобранных по этому навыку.
5. Ниже или на соседней вкладке находятся статистика Challenge, дневная цель и серия дней.
6. Если точность по навыку ~80% и выше, приложение предлагает повысить сложность.

### 7.7 Продолжение на другом устройстве
1. Пользователь работает с телефона: размечает график в Терминале и решает задания.
2. На ноутбуке открывает сайт и входит тем же способом (Google или magic link).
3. Приложение подгружает разметку терминала, прогресс, журнал ошибок и настройки из аккаунта.
4. Пользователь продолжает с того же места; новые данные снова сохраняются в аккаунт и видны на телефоне.
5. Незавершённое задание (например, Challenge в процессе) на другом устройстве **не** переносится **(предложение; OQ-17)**.

## 8. Критерии приёмки MVP

MVP принят, когда выполнены все пункты ниже и проверены на реальном телефоне пользователя через превью Vercel.

### 8.1 Сценарии Given/When/Then

**AC-01 Загрузка данных браузером**
- Given: пользователь открыл сайт на телефоне с доступом к Binance.
- When: он открывает график BTCUSDT 1H.
- Then: свечи и объём загружены запросами из браузера к Binance USDⓈ-M; запросы к Binance с серверов Vercel отсутствуют; график отображается.

**AC-02 Незакрытая свеча**
- Given: открыт живой график в терминале.
- When: приходят обновления по WebSocket.
- Then: последняя свеча обновляется и визуально помечена как незакрытая; после закрытия пометка снимается, свеча не дублируется.

**AC-03 Недоступность Binance**
- Given: запросы к Binance блокируются (сеть недоступна или 451).
- When: пользователь открывает график.
- Then: показано понятное сообщение с причиной и кнопкой повтора; интерфейс остаётся работоспособным.

**AC-04 Привязка разметки**
- Given: на графике 1H стоит метка Swing High.
- When: пользователь прокручивает, масштабирует график и переключает таймфрейм на 15m.
- Then: метка остаётся на своём времени и цене; объект сохранён с координатами время/цена.

**AC-05 Управление разметкой касаниями**
- Given: пользователь на телефоне выбрал инструмент Order Block.
- When: он протягивает прямоугольник, затем перемещает и удаляет его.
- Then: объект создаётся, перемещается и исчезает; область касания не меньше 44×44 px.

**AC-06 BOS по закрытию тела**
- Given: на данных из data.binance.vision есть свеча, фитиль которой пробил уровень, а тело закрылось внутри.
- When: алгоритм ищет BOS.
- Then: BOS не фиксируется; на свече, чьё тело закрылось за уровнем, BOS фиксируется.

**AC-07 Сравнение разметки Market Structure**
- Given: пользователь отметил Swing High на свече, отстоящей от эталона на 2 свечи.
- When: он нажимает «Проверить».
- Then: отметка засчитана совпавшей; отметка со смещением на 3 свечи засчитана лишней, а эталонный swing — пропущенным (допуск ±2, значение уточняется в архитектуре).

**AC-08 Скрытое будущее в Challenge**
- Given: запущен сценарий Challenge на 1H.
- When: пользователь переключает таймфреймы на 15m, 4H и 1D и прокручивает вправо.
- Then: ни на одном таймфрейме нет свечей позже момента решения; дата не отображается.

**AC-09 Обязательные SL/TP**
- Given: пользователь выбрал LONG и не поставил SL или TP.
- When: он пытается подтвердить решение.
- Then: подтверждение заблокировано, сообщение объясняет, что нужно поставить SL и TP; для WAIT подтверждение доступно без SL/TP.

**AC-10 Проигрывание и результат в R**
- Given: подтверждена позиция LONG с SL и TP.
- When: проигрывание доходит до SL, TP или лимита времени.
- Then: проигрывание останавливается; результат показан в R нейтральным цветом; оценка качества решения показана отдельно от исхода.

**AC-11 Допуск уровня Price Action**
- Given: эталонный уровень задан в цене P.
- When: пользователь проводит уровень на расстоянии не более ~0.3% от P.
- Then: ответ засчитан верным; уровень за пределами допуска засчитан неверным.

**AC-12 Разбор из шести частей**
- Given: пользователь сделал ошибку в любом модуле.
- When: открывается разбор.
- Then: нижняя шторка содержит шесть частей (верность, что понято верно, ошибки, почему ошибка, как правильно, принцип); индикаторы верно/неверно различаются иконкой и формой, не красным/зелёным.

**AC-13 Терминал и проверка разметки**
- Given: пользователь на телефоне поставил метки на ETHUSDT в терминале.
- When: он открывает сайт на ноутбуке под тем же аккаунтом и нажимает «Проверить мою разметку».
- Then: метки на месте; проверка использует только закрытые свечи и возвращает 6-частный разбор.

**AC-14 Прогресс и «Слабые места»**
- Given: пользователь выполнил не менее 10 заданий с ошибками в разных навыках.
- When: он открывает «Прогресс».
- Then: первым показан экран «Слабые места» с навыками, отсортированными по точности; журнал ошибок содержит записи.

**AC-15 Мягкая серия**
- Given: пользователь выполнял дневную цель три дня подряд, пропустил один день и выполнил цель на пятый.
- When: открывается экран серии.
- Then: серия не обнулена из-за единственного пропуска.

**AC-16 Вход и изоляция данных**
- Given: два разных пользователя вошли в систему.
- When: каждый запрашивает разметку и прогресс.
- Then: каждый видит только свои данные; прямой запрос чужих строк к БД отклоняется правилами RLS.

## 11. План MVP

Каждая веха заканчивается Pull Request с превью-ссылкой Vercel; в `main` вливает пользователь. Порядок следует заданному в задании. Архитектура и ADR-решения принимаются на следующем этапе до начала M0.

| Веха | Содержание | Результат для проверки на телефоне |
|---|---|---|
| M0 | Каркас (Next.js + TypeScript, Vercel), структура репозитория, ресурсы текстов, загрузка данных (REST+WebSocket), обработка пропусков/дубликатов, незакрытая свеча, прототип проверки Binance из браузера на телефоне | Страница показывает живые и исторические свечи; сообщение об ошибке при недоступности Binance |
| M1 | График (Lightweight Charts, объём, темы, цвета) и слой разметки (инструменты, касания, перемещение, удаление, привязка время/цена) | Размечать график пальцем; метки не «уезжают» при зуме и смене таймфрейма |
| M2 | SMC-алгоритмы и Price Action-модели в отдельной TS-библиотеке с unit-тестами на данных data.binance.vision | Отчёт тестов в PR; отладочная страница показывает найденные алгоритмом структуры |
| M3 | Market Structure Analyzer: «Разметка» и «Вопрос», сравнение с допуском, 6-частный разбор, нижняя шторка | Полная сессия Market Structure |
| M4 | Price Action Trainer: «Найди модель», «Проведи уровень», «Контекст» | Задания трёх типов с разбором |
| M5 | Trading Challenge: сценарии, скрытое будущее, SL/TP, обоснование, проигрывание, R, оценка качества, 3 сложности | Полный цикл Challenge |
| M6 | Свободный терминал: любая пара USDⓈ-M, живой график, «Проверить мою разметку» | Терминал с проверкой разметки |
| M7 | Авторизация (Google + magic link), сохранение разметки, прогресс (навыки, журнал ошибок, адаптивная подборка, «Слабые места», статистика Challenge, повышение сложности, дневная цель, мягкая серия), синхронизация, RLS | Продолжение на другом устройстве |
| M8 | Интеграция и QA: проверка критериев приёмки раздела 8, производительность, доступность (дальтонизм), Impeccable-проверка, финальная стабилизация | Приёмка MVP по AC-01..AC-16 |

**Предложение:** вынести авторизацию (часть M7: вход, профиль, RLS) раньше — после M1 или M2. Причины: объекты разметки, попытки и прогресс с самого начала привязываются к `user_id` (модель данных сразу многопользовательская); RLS проверяется с первых таблиц; терминал и сессии заданий (M3–M6) могут сразу сохранять данные, а не переписываться позже. Это изменение порядка требует подтверждения (OQ-18). Остальное содержание M7 (расчёт прогресса) остаётся в конце.

Зависимости от действий пользователя: подключение репозитория к Vercel (до M0); создание проекта Supabase (до начала вехи с авторизацией).
