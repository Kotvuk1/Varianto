# ADR-0007: Правила исхода сделки Challenge (drill-down)

Статус: принято (2026-11-03). Источник: решения пользователя; `ARCHITECTURE.md` §4.3 (`resolveTrade`); `PRD.md` FR-TC-11..14, FR-TC-25, OQ-09, OQ-10.

## Контекст
Свеча не хранит порядок движения внутри себя. Если за свечу задеты и SL, и TP, исход по OHLC неоднозначен. Нужно детерминированное правило без допущений «в пользу» или «против» пользователя.

## Решение
Условия (решения пользователя):
- Вход по `close` последней видимой свечи (она общая для всех ТФ, см. ADR-0006 п.4); комиссии, funding и проскальзывание не учитываются.
- Дата сценария раскрывается после разбора (в ответе `grade`).

`resolveTrade(position, futureProvider)`:
1. Идём по будущим свечам выбранного ТФ после `T`. Касание: для LONG SL задет, если `low <= sl`, TP — если `high >= tp`; для SHORT — `high >= sl` и `low <= tp`. Равенство считается касанием. Заполнение происходит по уровню (R точно -1 или +RR), без проскальзывания.
2. Если в свече задет только один уровень — исход определён.
3. Если задеты оба — drill-down на 1m в пределах этой свечи: берём первую 1m-свечу, где задет хотя бы один уровень.
4. Если и в этой 1m-свече задеты оба — drill-down на aggTrades за эту минуту: первая сделка по времени (`transact_time`, затем `agg_trade_id`), цена которой достигла SL или TP, определяет исход. Одна сделка имеет одну цену, поэтому SL и TP одновременно она задеть не может.
5. Лимит времени (OQ-09): если до конца окна исход не определён — закрытие по `close` последней свечи окна, `R = (exit - entry) / |entry - sl|` со знаком по стороне, `outcome = 'timeout'`.
6. R: `1R = |entry - sl|`; SL даёт -1R; TP даёт `+|tp - entry| / |entry - sl|`.
7. WAIT: R не считается; оценка по правилам структуры (были ли условия для входа по эталонному алгоритму; формулу фиксирует `ALGORITHMS.md`). Будущее для WAIT всё равно возвращается для проигрывания и разбора.
8. Результат не зависит от ТФ обхода: drill-down доводит исход до точности сделок (инвариантный тест: обход по 15m и по 1m даёт одно решение). Реализация вправе идти сразу по 1m.
9. Ответ содержит `resolution.method`: `candle` | `drill-1m` | `drill-aggtrades` | `conservative-sl` | `timeout` — для прозрачности разбора.

Параметры лимита времени (предложение, зафиксировано в `ALGORITHMS.md` §14.4): число свечей выбранного ТФ в окне 15m: 96, 1h: 72, 4h: 60, 1d: 30 (OQ-09).

## Рассмотренные альтернативы
| Вариант | Почему отклонён |
|---|---|
| Всегда считать SL первым (консервативно) | Систематически искажает статистику R и оценку SL/TP-логики. |
| Всегда считать TP первым | То же, в обратную сторону. |
| Определять по направлению свечи (бычья - сначала low) | Эвристика, ложная для части свечей. |
| Только 1m без aggTrades | Остаются случаи, когда обе цены внутри одной минуты. |

## Последствия
- Нужен чтение daily aggTrades на сервере в редком случае (обе цены в одной минуте); размер zip около 14 МБ за сутки BTCUSDT (ADR-0004) — потоковая распаковка, остановка после нужной минуты; время и память проверить на M0.
- Если aggTrades недоступен или чтение не уложилось в лимит функции (решение оркестратора 2026-11-03): засчитывается SL (консервативно), `resolution.method = 'conservative-sl'`, разбор явно сообщает «внутри минуты порядок не определён — засчитан стоп». Пользователь не остаётся без результата; случай крайне редкий.
- Отсутствие комиссий упрощает R, но завышает результат частых сделок; это сознательное упрощение учебной симуляции.
- Для 1m и aggTrades нужны фикстуры спорных свечей (`fixtures/`) и golden-тесты `resolveTrade`.

## Открытые вопросы (закрыты: `docs/specs/ALGORITHMS.md`)
- Лимиты времени по ТФ и сложности (OQ-09): закрыто, значения 96 / 72 / 60 / 30 свечей (15m / 1h / 4h / 1d) одинаковы для всех сложностей (ALGORITHMS §14.4).
- Касание при точном равенстве цены: подтверждено, равенство = касание (ALGORITHMS §15, п. 1).
