# ADR-0005: Stateless-задания с подписанными токенами; будущее только на сервере

Статус: принято (2026-11-03); уточнение «T шифруется» помечено как расширение (см. Открытые вопросы). Источник: `ARCHITECTURE.md` C3, C4, §5.3, §7; решение пользователя: дата Challenge раскрывается после разбора.

## Контекст
- Challenge не должен раскрывать будущее и дату (FR-TC-02, FR-TC-04, AC-08); проверку ответа выполняет детерминированный `@tl/core` (принцип 1).
- До M7 нет БД на сервере (C4, C5); серверу нельзя хранить состояние сессий.
- Клиент не должен иметь возможности подделать задание или результат (R-08).

## Решение
1. `POST /api/tasks/{module}/next` выбирает момент `T` (по seed, из архива, ADR-0004), проверяет пригодность ситуации через `@tl/core` и возвращает только прошлое (`closeTime < T`, `sliceAt`, ADR-0006) и `taskToken`.
2. `taskToken` — stateless-токен формата `v1.<header>.<sealed>.<mac>`:
   - `header` (открытый JSON): `module`, `symbol`, `difficulty`, `algoVersion`, `iat`, `exp` (версия формата `v` — префикс);
   - `sealed` — AES-256-GCM от `{ T, seed, shiftMs, tf?, params }`; клиент не может прочитать `T`;
   - `mac` — HMAC-SHA256 над `v1.<header>.<sealed>`; ключи шифрования и MAC выводятся из `TASK_SIGNING_SECRET` (env Vercel) с разными метками.
3. `POST /api/tasks/{module}/grade` проверяет `mac` и `exp`, расшифровывает, восстанавливает ситуацию из архива, считает эталон в `@tl/core`, возвращает `GradeResult` + разбор. Для Challenge в ответе также будущие свечи (проигрывание) и раскрытая дата.
4. Скрытая дата: время свечей и якорей в ответе `next` сдвинуто на секретный `shiftMs` (кратен 1 суткам, чтобы сетка 4h/1d осталась выровненной). Метки пользователя приходят на той же сдвинутой шкале; сервер возвращает их в реальное время. Реальная дата — только в `grade` (после разбора).
5. Сервер не хранит ничего; всё восстанавливается из токена и архива. `exclude[]` — список непрозрачных `taskId` (хэш от `symbol+T`), по которым клиент исключает повторы.
6. Ответы `grade` не раскрывают параметры эталона сверх нужного для разбора (`ARCHITECTURE.md` §7).

## Рассмотренные альтернативы
| Вариант | Почему отклонён |
|---|---|
| Хранить сессии заданий в БД | Нет БД до M7; усложняет бесплатный тариф. |
| Отдавать клиенту всё будущее сразу и скрывать в UI | Нарушает C3: будущее виден в DevTools. |
| Проверка на клиенте | Подмена результата; для одного владельца допустимо, но противоречит архитектуре (R-08, C7). |
| Токен только подписан, `T` открыт | Клиент читает дату из payload (base64) — раскрывает сценарий. |
| `T` выводится из `seed` при проверке | Пересчёт выбора требует повторного обхода архива; шифрование дешевле. |

## Последствия
- Плюс: нет серверного состояния; масштабируется на Hobby.
- Плюс: дата и будущее недоступны до `grade`.
- Минус: повтор — один и тот же токен можно отправить в `grade` многократно; клиент, вызвав `grade` с произвольным ответом, увидит будущее. Приемлемо для одного владельца; смягчения (`exp`, учёт попыток на клиенте) — Открытые вопросы.
- Минус: ротация `TASK_SIGNING_SECRET` инвалидирует все выданные токены (приемлемо: `exp` короткий); версия `v` в токене допускает смену формата.
- Минус: `algoVersion` в токене фиксирует версию эталона для задания; сервер должен уметь исполнять версию из токена или отклонить токен ошибкой (политика — Открытые вопросы).
- Запрет: `T`, `seed`, `shiftMs` не логируются на клиенте и не попадают в URL.

## Открытые вопросы
- Подтвердить шифрование `T` внутри токена (расширение формулировки «HMAC-подписанный `{... T ...}»).
- `exp` токена: предложение 24 часа.
- Что делать с токеном, у которого `algoVersion` старше текущей (исполнять старую версию ядра или считать токен просроченным).
- Защита от повторного `grade` на один токен (без хранилища невозможна; при многопользовательском режиме потребуется БД или одноразовые nonce).
