# Стратегия тестирования — Trading Lab

Версия 0.1, 2026-11-03. Основание: `docs/ARCHITECTURE.md` (§4, §5, §9, §10), `docs/PRD.md` (NFR-TEST, AC-01..AC-16, AC-X). Агенты и их зоны: `docs/AGENTS.md`.

## 1. Принципы

1. Правильность определяет детерминированный алгоритм; тесты фиксируют его поведение на реальных данных.
2. Только реальные свечи. Данные для тестов берутся из `data.binance.vision`. Тесты не обращаются к Binance API напрямую (NFR-TEST-04).
3. Ничто не считается готовым без запуска тестов и показа их вывода.
4. Тест пишется до реализации (TDD) в `packages/core`; в остальных зонах — по возможности.
5. Тесты детерминированы: никаких обращений к сети, текущему времени и `Math.random` без подмены (seed/clock injection).

## 2. Пирамида

| Уровень | Что проверяет | Инструмент | Зона | Доля |

## 3. Фикстуры

Каталог `fixtures/` содержит реальные файлы klines и aggTrades из `data.binance.vision` (USDⓈ-M futures).

- `fixtures/README.md` обязателен. Для каждого файла: URL источника, symbol, timeframe, период, дата скачивания, SHA-256, назначение (какие тесты используют).
- Файлы хранятся в исходном виде (CSV; zip — если нужен тест распаковки). Преобразованные JSON допускаются только как производные с указанием исходного файла и скрипта преобразования.
- Синтетические свечи запрещены. Исключение: минимальный юнит-кейс граничного условия (например, две свечи с равным high), которого нет в реальных данных. Такой кейс:
  - лежит в файле/объекте с префиксом `synthetic_`;
  - помечен в тесте комментарием `// SYNTHETIC: <причина, почему реальных данных недостаточно>`;
  - не используется в golden-тестах, E2E и скриншотах.
- Для E2E: записанные реальные ответы Binance (REST klines, WS-сообщения) хранятся в `fixtures/recorded/` с датой записи; в интерфейсе тестового режима данные помечаются `fixture`.
- Размер фикстур ограничивается: берутся только нужные периоды (не весь месяц, если достаточно дня).

## 4. Обязательные наборы тестов

### 4.1 Инвариант агрегации таймфреймов
Агрегация 1m → 15m → 1h → 4h → 1d совпадает с нативными свечами Binance из фикстур: `open`, `high`, `low`, `close` — точно; `volume`, `quoteVolume` — с допуском округления; `trades` — точно. Проверяется на нескольких периодах, включая границу суток UTC.

### 4.2 `sliceAt(series, T)`
- Нет свечей с `closeTime >= T` среди закрытых.
- Старшие ТФ содержат частичную свечу из 1m `[openTime, T)` с `closed=false`; её OHLC совпадает с ручным расчётом по фикстуре.
- Единая точка «сейчас»: для любого T срезы всех ТФ согласованы (максимум `high` частичной свечи не превышает максимум 1m до T).
- Свойство: ни одно значение в срезе не зависит от данных после T (срез по T и срез по T на усечённых данных идентичны).

### 4.3 Нормализация (`market-data`)
- Дубликаты: остаётся последняя версия; закрытая свеча побеждает незакрытую.
- Пропуски: обнаруживаются по шагу ТФ, дозапрашиваются; если не получены — помечаются `gap`, свечи не выдумываются.
- Незакрытая свеча: `closed=false` для последней свечи, смена на `true` не создаёт дубликат (AC-02).
- Сортировка по `openTime`; все времена в UTC.
- WS: записанные реальные сообщения `kline` (`k.x` true/false); переподключение с экспоненциальной задержкой; после переподключения REST-догрузка с последнего `openTime` без дублей и пропусков (NFR-REL-02); fallback на polling.
- CSV архива: проверка заголовков, понятная ошибка при смене формата.

### 4.4 Golden-тесты SMC/PA
- Участки реальных данных размечает вручную Technical Analyst по `docs/specs/ALGORITHMS.md`; разметка хранится рядом с фикстурой (`*.golden.json`: marks, ALGO_VERSION, автор, дата, обоснование каждой метки).
- Тест сравнивает выход алгоритма с golden точно. Изменение golden допустимо только через Technical Analyst с повышением `ALGO_VERSION` при смене семантики.
- Покрытие: swing (по сложностям), HH/HL/LH/LL, BOS/CHoCH (в т.ч. фитиль без закрытия тела — AC-06), internal/external, sweep, OB, FVG, шесть PA-моделей, уровни (допуск ~0.3%, AC-11), допуск ±2 свечи в `gradeMarks` (AC-07).
- Свойства: детерминизм (двойной запуск идентичен, NFR-TEST-03); алгоритмы используют только закрытые свечи (FR-DATA-08).

### 4.5 `resolveTrade`
- LONG/SHORT: исход SL, TP, лимит времени; результат в R.
- Одна свеча задевает SL и TP: drill-down по ТФ вниз до 1m; если и на 1m обе цены в одной свече — aggTrades из архива; результат содержит момент срабатывания на младшем ТФ. Фикстуры — реальные случаи, найденные в архиве (скрипт поиска хранится в `fixtures/`).
- Вход по закрытию последней видимой свечи; комиссии не учитываются.
- Свеча, где задет только один уровень, drill-down не запускает.
- Корректность сторон SL/TP (FR-TC-08), WAIT без SL/TP.

### 4.6 Интеграционные тесты API
- Route handlers вызываются напрямую; `ArchiveSource` читает локальные фикстуры вместо сети.
- `/api/tasks/*/next`: ответ не содержит данных позже T и реальной даты (относительная шкала, AC-08); токен подписан.
- `/api/tasks/*/grade`: подделанный/просроченный токен отклоняется; ответ раскрывает дату и будущее только после grade; не раскрывает параметры эталона сверх необходимого.
- Валидация `zod`: невалидные входы, лимит размера, whitelist символов.
- `Cache-Control: immutable` для закрытых периодов `/api/history`; задания строятся только по данным старше 2 суток.
- Rate limit.

### 4.7 Прочие unit-тесты
- `LocalRepository` на `fake-indexeddb`: контракт `Repository` один и тот же для `LocalRepository` и (в M7) `SupabaseRepository`; импорт локальных данных при первом входе идемпотентен.
- Форматирование времени: хранение UTC, показ в локальном поясе (OQ-05) — тест с разными `TZ`.
- Тексты: линтер запрещает жёсткие строки в компонентах (NFR-I18N-01).

## 5. E2E (Playwright)

- Viewport: 390x844 (mobile, touch) и 1440x900 (desktop). Каждый сценарий выполняется на обоих.
- Сеть Binance подменяется записанными реальными ответами (`page.route` / WS-мок на записи). Реальный Binance в CI не вызывается.
- Базовые сценарии: загрузка графика и объёма; незакрытая свеча (AC-02); ошибка недоступности Binance и повтор (AC-03); создание, перемещение, удаление метки с касанием, область ≥ 44x44 (AC-05); метка сохраняется при смене ТФ (AC-04); Challenge: скрытое будущее на всех ТФ, обязательные SL/TP, проигрывание, R (AC-08..AC-10); разбор из шести частей в шторке (AC-12); отсутствие горизонтальной прокрутки от 360 px (NFR-RESP-02).
- Каждый скриншот/видео этапа подписывается источником данных (например, «Binance Futures BTCUSDT 1h, data.binance.vision, 2025-03-01..2025-03-07, fixture»). Скриншоты без подписи не принимаются.
- До подключения Vercel артефакты Playwright (скриншоты/видео) прикладываются к PR как подтверждение этапа.

## 6. Визуальная проверка и доступность

- Скриншоты ключевых экранов в тёмной и светлой темах, mobile и desktop.
- Impeccable `audit` и `critique` для каждого UI-этапа; замечания уровня высокий/критичный устраняются до приёмки (FR-UI-10).
- Контраст WCAG AA (NFR-A11Y-01), симуляция дальтонизма для синих/оранжевых свечей (NFR-A11Y-02), смысл меток не только цветом (NFR-A11Y-04), красный/зелёный не используется как победа/поражение (AC-X-07).

## 7. Критерии «готово» для вехи

Веха принимается, когда одновременно выполнено:
1. Все тесты зелёные: unit, integration, e2e (вывод запуска приложен).
2. `typecheck` (strict), `lint`, `build` без ошибок.
3. Покрытие `packages/core` не ниже порога (раздел 9).
4. AC вехи (PRD §8, ROADMAP) проверены QA Engineer независимо — не автором кода.
5. Для вехи с UI: скриншоты mobile и desktop с подписью источника, Impeccable audit/critique без блокирующих замечаний.
6. Нет синтетических данных вне помеченных `synthetic_`-кейсов; нет секретов в репозитории (AC-X-03).
7. Обновлены документация и граф (`graphify update .`).
8. Отчёты агентов содержат результат запуска тестов; отсутствие запуска означает «не готово».

## 8. CI (GitHub Actions)

Workflow на каждый PR и push в `main`, кэш pnpm:

| Job | Команда | Зависит от |
|---|---|---|
| lint | `pnpm lint` | — |
| typecheck | `pnpm typecheck` | — |
| unit | `pnpm test` (Vitest, `packages/*`, `apps/web`; покрытие core) | — |
| build | `pnpm build` (`next build`) | lint, typecheck, unit |
| e2e | `pnpm e2e` (Playwright, оба viewport, записанные ответы; артефакты скриншотов/видео и trace загружаются) | build |

Дополнительно: сканирование секретов; проверка, что в тестах нет обращений к `fapi.binance.com`/`fstream.binance.com`. Merge в `main` — только пользователем, при зелёном CI.

## 9. Покрытие

Предложение: `packages/core` — не менее 90% строк (Vitest coverage, v8) и не менее 85% ветвей; снижение порога блокирует CI. `packages/market-data` — не менее 80% строк. Для `apps/web` порог не задаётся, важнее E2E по AC. Покрытие не заменяет golden-тесты: число строк не доказывает правильность определений SMC.

## 10. Производительность

Бенчмарк unit-теста: расчёт SMC на 1000 свечей не более 100 мс (NFR-PERF-03), измеряется в CI с допуском; прокрутка/зум и 200 объектов разметки (NFR-PERF-01, 04) проверяются профилированием и ручным замером на устройстве пользователя после подключения Vercel.
